# PAGE-PERF-PLAN-20261012：页面加载定位与加速方案

日期：2026-10-12（马来西亚）。本轮为定位与建议，**没有修改或部署应用**。固定字段证据（本地测试产物，不入库：`./PAGE_PERFORMANCE_EVIDENCE.json`）保留实际 GET、容器运行时间与源码分析；没有登录、读取数据库或 Secret、调用模型。

## 结论与证据边界

当前部署没有登录链冷启动证据。服务器内部读取 HTML 约14–17ms，客户端公网 HTML约1.03–1.86s，主要组件包下载约1.28–1.71s。已测样本的成本主要在公网连接／往返及前端资源；**这些是独立curl请求，不能相加为浏览器首屏时间，也不能解释未抓取的那次长等待**。浏览器执行／渲染、缓存命中和当时登录接口瀑布尚未测量。

VM连续运行约6.1天；前端/Caddy约30.6小时，gateway/auth约70.8小时，均0重启、至少1副本；17/17 Deployment Ready，仅data HPA min1/max2，没有缩至0证据。节点无资源压力。当前没有证据支持先扩CPU/RAM或把数据库速度认定为匿名登录首屏瓶颈。

## 1. 慢在哪里

| 环节 | 已知事实 | 可以得出的结论 |
|---|---|---|
| 服务器内部请求登录HTML | 私网14.5ms／回环16.5ms（包含TLS建立），VM经域名87.1ms | 当前静态站点响应快，没有等待容器启动；这些不是纯CPU处理时间。 |
| 客户端公网HTML | 首次DNS443ms，TLS完成累计1.361s，总1.862s；再次总1.033s | 此采样存在DNS、建连／TLS和往返成本；不是页面内绘制时间。 |
| 主要前端资源 | component JS gzip后232,728bytes，实测总1.708s／1.275s；最新TTFB682ms、body阶段约593ms | 首访静态传输有成本；网络和资源大小都值得优化。 |
| 浏览器渲染 | 未取得浏览器性能瀑布、长任务或首次可见时间 | 不能认定浏览器CPU／渲染是实际故障原因。 |
| 登录／恢复会话 | 无token的登录路由无需业务API；缓存token存在时可能等待/auth/userInfo或refresh | 是否导致当时卡住未知，不能用源码可能性代替实际请求记录。 |
| 异常重试 | 默认请求60s（登录单独180s），最多6次重试，间隔5/15/30/45/60/60s | 间隔本身累计可达215s，异常请求可能等数分钟；没有证据证明用户当次命中了重试。 |

最新主要组件GET为HTTP2 200、0重定向、`Content-Encoding: gzip`、`Cache-Control: public, max-age=31536000, immutable`、`Vary: Accept-Encoding`，所以**压缩与哈希资源长期浏览器缓存已经启用**，不把重复开启二者列为新增收益。

## 2. 可以立即采用的访问办法

1. 使用相同浏览器的普通窗口、保留站点缓存，收藏当前HTTPS地址；正常再次打开时允许复用已有哈希资源。不要把清空缓存／强制刷新作为日常提速方式。当前实测已是HTTPS直达、0重定向，收藏本身不会神奇缩短网络时间。
2. 同一设备与链接对比Wi-Fi和手机热点，或对比已使用的代理路线；如果有代理，只做开／关或路线对照选择更快者。网络路线／代理是否为本次原因尚未确认，不笼统断言关代理必定更快。
3. 同一网络做Safari／Chrome与内置浏览器对照，区分浏览器缓存／扩展与公网链路。尚未实际完成这些对照，不保证某浏览器必然更快。

不要直接替换成HTTPS IP地址绕过域名；现有站点证书按域名验证，域名／TLS必须保持正确。当前DNS首样本仅解释约0.44秒，不足以解释数分钟；更换DNS最多是可测的连接阶段优化，不能称确切根因。

## 3. 项目侧优化顺序（候选，待实施）

### A. 首先减少登录页公共包与图标

[main.js](../../../frontend/src/main.js)全量注册293个Element Plus图标；生产同名chunk确实保留未用于登录的图标。匿名登录构建图为5 JS＋4 CSS，解压后1,085,827bytes，**不是实际网络下载量**；本地gzip估算299,956bytes，未完整验证浏览器实际传输总量。公共JS724,565bytes，公共CSS227,466bytes，是主要组成。

方向：改为显式／按需图标引用，并评估[vite.config.js](../../../frontend/vite.config.js)的公共chunk组织，让登录所需组件与管理页面增量合理分离。保持现有懒加载和消息框样式。图表包不在匿名登录静态依赖图，不把删除图表功能列为登录提速方案。拆包不是越多越好，必须以新构建依赖图、压缩体积、请求数和浏览器首屏验证取舍。收益尚未测量，不承诺某个百分比。

### B. 调整旧Render重试文案及等待预算

[request.js](../../../frontend/src/utils/request.js)／[retry.js](../../../frontend/src/utils/retry.js)将429、502/503/504、无响应和超时归为冷启动，显示“服务正在唤醒，首次访问2–3分钟”。这只能证明网络／HTTP失败条件，不能证明K3s休眠。[prewarm.js](../../../frontend/src/utils/prewarm.js)为后台请求，不await，不阻塞mount；生产额外Render URL未注入，不能称正在串行唤醒七服务。

[auth.js](../../../frontend/src/api/auth.js)另给登录180秒timeout并启用retryUnsafe；180秒是失败等待上限，不是每次登录固定耗时，也不是本轮实测登录请求。

方向：Kamatera使用中性网络错误提示、明确的总等待上限和手动重试；部署环境确实需要冷启动时保留独立配置。重试只用于可确认重放的请求，保持非幂等业务写入及认证会话隔离约束。**这能缩短异常时的无效等待，不会改善一次成功GET本身的网络速度。** 不仅把每次timeout改短却仍保留长重试链，也不从网络超时推断后端未执行。

### C. 再评估静态CDN

候选是拥有可控制域名后，把公开哈希JS／CSS交给Cloudflare静态缓存，业务／登录API继续走当前鉴权链并明确绕过共享缓存；不配置全站Cache Everything。Cloudflare默认按扩展名缓存JS／CSS，HTML与JSON默认不缓存。[官方缓存规则](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)。常规DNS接入需要添加域名并在注册商更新nameservers；当前nip.io子域名不受本项目控制，不能直接当自己拥有的zone接管。[官方DNS接入](https://developers.cloudflare.com/dns/get-started/)。

CDN是后续候选；域名和账户设置、TLS、SSE／鉴权／API缓存边界需要明确配置与回归，没有执行或收费操作。缓存命中可能减少静态回源成本，但新路线不保证所有网络都更快，应在马来西亚目标网络实测。若没有域名，先做A/B无需新增外部资源；前端搬到其他平台则还要解决同源/api路由，不能当零改动方案。

## 4. 验证与上线判据

候选实现前先建立浏览器匿名冷缓存／暖缓存基线，至少各3次，记录HTML／资源DNS、连接、TTFB、transfer、首屏可见和长任务；登录后单列/auth/login、/auth/userInfo与看板GET，不触发Agent／Groq。Resource Timing支持拆分网络与传输指标，但跨源时部分字段受权限限制。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming)。只保存固定耗时与资源大小，不留Authorization、Cookie或师生正文。

A完成后验证图标在登录／侧栏／图表／弹窗正常，真实冷缓存JS/CSS字节和请求依赖减少，暖缓存复用未倒退；B验证成功请求、网络超时、429/502/503/504、取消、写操作不重复、401不误清新会话；C验证静态命中、HTML版本更新、API不共享缓存、SSE与权限正常。
